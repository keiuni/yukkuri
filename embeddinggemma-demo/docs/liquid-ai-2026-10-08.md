# Liquid AI の d1 と LFM2.5-2.6B の検証（2026-10-08）

Liquid AI が公開した 3 つのモデルを、これまでの検証と同じ環境（クラウドコンテナ、CPU 4 コア、GPU なし）で試した記録です。

- **d1-3B / d1-omni-600M**: 「判断モデル」。文章を書かず、状態と質問（はい/いいえ・選択肢・段階評価）から確率つきの答えを 1 回の計算で返します。Jev と同じ役割のモデルです。
- **LFM2.5-2.6B**: デバイス上で動くエージェント向けの言語モデル。計画を立て、道具を呼び出します。

## 結論

1. **d1-3B は「Jev の役」として精度が高いが、CPU では遅い。**
   前回のブラウザエージェントの判断役に入れると 6 タスク中 5 つ成功し、21 手中 20 手で正しい要素を選びました。
   指示文を英語にしても選択は 1 手も変わらず、確率が出るので「迷っている」手順（領収書で 0.39 対 0.32）も見えます。
   ただし GPU のないこの環境では 1 回の判断に 11〜12 秒かかり、EmbeddingGemma（6/6、0.1 秒）の約 100 倍です。モデルカードの「1 問 30 ms」は GPU での値です。
2. **d1-omni-600M はこの用途では使えなかった（1/6）。** モデルカードの Decision Index も 15.95 と低く、d1-3B（48.57）とは別物と考えたほうがよい結果です。
3. **LFM2.5-2.6B は、投稿の数字はモデルカードどおりだが、日本語のブラウザ操作では Gemma 4 E2B を超えなかった。**
   判断役で 2/6（Gemma 4 E2B は 3/6）、手順を書く役で 2/6（同 3/6）、本来の使い方である道具呼び出しで直接操作しても 2/6 でした。
   道具呼び出しの形式は正確でしたが、要素の取り違え・設定の漏れ・終わりの判断で失敗しました。
   推論モデルで毎回考えてから答えるため、この CPU では 1 回 20 秒〜4 分かかります（判断役のときの中央値は 78 秒）。
4. **ブラウザで動くのは LFM2.5-2.6B だけ。** ONNX 版（q4 1.85 GB）が WebGPU で読み込めて生成もできました。d1 は ONNX がなく、llama.cpp のサーバーでしか動きません。
5. **いまの手元の条件（CPU やブラウザ）では、「Jev の役」には EmbeddingGemma が最も実用的です。**
   d1-3B は確率が付く分だけ判断の中身がわかりやすく、GPU や NPU のある端末なら有力な選択肢です。

d1 は `llama-server` の `/v1/systemone`（TypeSafe の Jev と同じ形の API）で答えを返します。d1-3B は Q8_0、d1-omni-600M は Q8_0、LFM2.5-2.6B は Q4_K_M です。

## 投稿の主張とモデルカード

### d1（Open d1）

| 投稿・図の内容 | モデルカード | この環境での確認 |
| --- | --- | --- |
| d1-3B はテキスト＋画像 | SigLIP2 の画像エンコーダー付き、画像ベンチマーク 11 種の平均 74.1 | テキストだけ試した |
| d1-omni-600M はテキスト＋画像、またはテキスト＋音声 | 画像と音声は同時には使えない（両方渡すとエラー） | テキストだけ試した |
| Decision Index: d1-3B 約 48.6、d1-omni-600M 約 16 | 48.57 と 15.95。どちらも「公式の採点器で自分たちが採点した値（リーダーボードへの提出ではない）」 | 採点はしていない |
| 図の上端: d1（hosted API）約 60、Jev 1.13（hosted API）約 57 | 公開されたのは 3B と 600M だけで、約 60 の d1 は API 版 | – |
| DGX から Jetson まで、リアルタイムに判断 | 1 問 8 ms（RTX 4090）、30 ms（Apple M5 Pro）、50 ms（Jetson Orin Nano） | CPU 4 コアでは 1 回の判断（候補約 20 個）に d1-3B で約 12 秒、d1-omni-600M で約 3 秒 |

d1 の説明どおり、答えは 1 回の計算で出て、生成トークンは 0 でした（`usage.output_tokens` が 0）。
モデルカードの例（二重請求の問い合わせ）では、返金の要求か 0.99、担当は「請求」0.98 と、例のとおりの答えになりました。

この CPU（Q4_K_M）での生成は毎秒約 10 トークンで、この質問に 45 秒かかりました。モデルカードの値は Ryzen AI Max+ 395 で毎秒 113 トークン、Apple M5 Max で 220 トークンです。

## ブラウザエージェントで試す（Jev の役と、手順を書く役）

前回作った、jev-ultrafast と同じ流れのエージェント（`agent/run.mjs`）に組み込みました。
6 つのタスク（宿泊予約、通販の領収書と商品検索、アカウント設定 2 つ、日本語版ウィキペディア）を、毎回タスクごとの検証で採点します。

### Jev の役（手順に合う操作を、候補の中から選ぶ）

手順は前回と同じ手順書（Claude が作成）です。判断役が受け取る情報は、どのモデルでも同じ（いまの手順と候補の一覧）です。

- d1 には、候補を名前つきの選択肢にした `choice` の質問を 1 つ渡します（状態は「手順: …」、指示は「この手順を実行するには、どの操作をすればよいですか？」）。
  プルダウンの項目選び（文字列で決まらないとき）も d1 に同じ形で聞きます。
- LFM2.5-2.6B と Gemma 4 E2B には、番号つきの候補表を見せて `{"id": 番号}` で答えさせます。

| 判断役 | 実行 | 成功 | 1 回の判断（中央値 / 最大） |
| --- | --- | ---: | ---: |
| EmbeddingGemma 300M（fp32） | onnxruntime（Node） | **6/6** | 0.11 秒 / 3.1 秒 |
| EmbeddingGemma 2（fp32） | onnxruntime（Node） | **6/6** | 0.13 秒 / 4.6 秒 |
| **d1-3B（Q8_0）** | llama.cpp | **5/6** | 12 秒 / 66 秒 |
| Gemma 4 E2B（q4） | onnxruntime（Node） | 3/6 | 7.4 秒 / 59 秒 |
| LFM2.5-2.6B（Q4_K_M） | llama.cpp | 2/6 | 78 秒 / 229 秒 |
| d1-omni-600M（Q8_0） | llama.cpp | 1/6 | 2.7 秒 / 28 秒 |

LFM2.5-2.6B 以外の最大値は、要素が約 150 個あるウィキペディアのページで「検索を実行する」を選んだときです（LFM2.5-2.6B の最大値は、答えが空になった手順）。
d1 の指示文を英語（「Step: …」「Which action carries out this step?」）にしても、d1-3B は 21 手すべてで同じ要素を選び、結果も同じ 5/6 でした。

**d1-3B** は 21 手のうち 20 手で正しい要素を選び、多くは確率 0.95 以上でした。
外したのは「2026年9月の注文の領収書を出す」で、「注文の詳細を見る」（0.39）を「9月の注文の領収書を発行する」（0.32）より上にしました（EmbeddingGemma は正解、Gemma 4 E2B は 10 月の注文を選んで失敗）。
精度は EmbeddingGemma に近いのですが、CPU では 1 回の判断が約 100 倍遅くなります。候補 20 個ほどの判断は約 400 トークンの入力を 3B のモデルに通すことになり、
この環境（CPU 4 コア、毎秒約 36 トークン）では 11 秒前後かかります。候補が 151 個あるウィキペディアのページでは 2,336 トークンでした。
モデルカードの速さ（Apple M5 Pro で 1 問 30 ms、3.4k トークンの状態で 640 ms）は GPU を使ったときの値です。

**d1-omni-600M** は確率が全体に低く（1 位でも 0.1〜0.3）、「この手順はもう済んでいる」を選びがちでした。指示文を英語にしても 1/6 のままで、成功するタスクが入れ替わっただけでした。
モデルカードでも Decision Index は 15.95 で、d1-3B（48.57）との差は大きいです。

**LFM2.5-2.6B** は `{"id": 番号}` の形式は守りましたが、「禁煙の部屋だけに絞り込む」で地名のリンク「札幌」を押す、「検索を実行する」で「カテゴリ一覧」を押すなど、要素の取り違えが目立ちました。
毎回考えてから答えるので、1 回の判断に中央値で 78 秒かかりました。1 回は答えが空でした（229 秒かかっており、2,048 トークンの上限まで考え続けたとみられます）。

### 手順を書く役（計画と完了の判定）

| 手順を書く役 | 判断役 | 成功 | 備考 |
| --- | --- | ---: | --- |
| Gemma 4 E2B | EmbeddingGemma 300M | 3/6 | 前回の結果。1 回の計画は 16〜44 秒 |
| LFM2.5-2.6B（JSON で手順を書く） | EmbeddingGemma 300M | 2/6 | 1 回の計画は 31〜244 秒 |
| LFM2.5-2.6B（道具呼び出しで直接操作） | LFM2.5-2.6B 自身 | 2/6 | 1 回の呼び出しは 23〜193 秒 |

**JSON で手順を書く方式**（Gemma 4 E2B と同じ指示）では、次の問題がありました。

- 宿泊予約では、道具を渡していないのに `[click(selector='ボタン「この条件で検索する」')]` という道具呼び出しを書き、行き先や日付の入力を飛ばしていきなり検索しようとした（計画として読めず失敗）。
- 「はい/いいえ」で答える達成の確認で、存在しない `google(query=…)` という道具を呼んだ（ウィキペディアで 4 回）。
- `{"step": "開く", "text": "注文履歴"}` や `{"step": "操作", "text": "メール通知スイッチをオフに"}` のように、手順の文が中身のない言葉になり、内容が値の欄に入った。
- 商品検索では 3 つの手順を正しく書いたのに、検索でページが変わったあとの確認で「はい（達成済み）」と答え、並べ替える前に終えた。

**道具呼び出しで直接操作する方式**（LFM2.5-2.6B の本来の使い方）は `agent/tools.mjs` で作りました。
ページの要素を番号つきで見せ、`type_text` / `select_option` / `set_switch` / `click` / `finish` の 5 つの道具を渡します。
道具の呼び出しの形式は崩れず（要素の番号が文字列になることはあった）、llama.cpp がそのまま読み取れました。設定の 2 タスクは、1 回の呼び出しで 3 つの操作（切り替え・選択・保存）をまとめて行い、成功しました。失敗は次のとおりです。

- 宿泊予約: 行き先・日付・泊数・検索・絞り込み・並べ替えまでできたが、「大人 2 名」を設定し忘れた。
- 領収書: 9 月の領収書のページまで行けたのに `finish` を呼ばず、注文履歴に戻った。
- 商品検索: 安い順に並べ替えたあと検索ボタンを押し直し、並び順を元に戻した。
- ウィキペディア: 最初に関係のないリンク「ウィキペディア」を押してしまった。

目標から手順を組み立てる部分と、終わったかどうかの判断は、Gemma 4 E2B と同じく 2〜3B クラスの生成モデルには荷が重いという結果です。
モデルカードの ToolSandbox などの高い値は英語の道具呼び出しのベンチマークで、この日本語のブラウザ操作では Gemma 4 E2B を上回りませんでした。

## スマホやブラウザで動くか

| モデル | ブラウザ（Web） | スマホのネイティブアプリ |
| --- | --- | --- |
| d1-3B | 公式の Web 版なし。ONNX がなく、`/v1/systemone` は llama.cpp のサーバー側の機能なので、ブラウザ内では動かない | GGUF を llama.cpp で。Q4_K_M で 1.67 GB。モデルカードの「エッジ」は Jetson と Apple M5 Pro で、スマホでの値はない |
| d1-omni-600M | 同上 | Q8_0 で 407 MB と軽いが、この検証では役に立たなかった |
| LFM2.5-2.6B | ONNX 版あり（WebGPU 専用）。q4 1.85 GB / q4f16 1.53 GB。公式の WebGPU デモあり | GGUF（Liquid AI の LEAP 用の設定つき）・MLX。モデルカードには「毎秒 30 トークンならスマホでもエージェントが動く」とある |

LFM2.5-2.6B の ONNX 版は、埋め込み表が GatherBlockQuantized（4bit）なので WASM（CPU）では動かず、WebGPU が必要です。
最大の重みは 4bit の埋め込み表（128,000 × 1,024 バイト = 131 MB）で、WebGPU の既定の 1 バッファの上限（128 MiB）にも収まります。
スマホ実行チェック（`phone.html`）に追加しました（q4f16 は f16 対応の GPU が必要）。

Pixel 7 の画面とソフトウェア WebGPU（SwiftShader、f16 なし、1 バッファ 1 GiB）で、q4 を実際に動かしました（`npm run phone-check -- lfm2.5-2.6b:q4:webgpu --tokens 8`）。

| モデル | 判定 | ダウンロード | 読み込み | 最初の 1 トークン | タブのメモリ |
| --- | --- | ---: | ---: | ---: | ---: |
| LFM2.5-2.6B q4（WebGPU） | 微妙（ダウンロードが 1.9 GB） | 1,873 MB | 15.8 秒 | 310 秒（ソフト GPU のため参考外） | 2.7 GB（ブラウザ全体 5.0 GB） |

読み込みと生成はできました。出力は「The user wants three short points about the」と、英語で考え始める文でした（8 トークンで打ち切り）。
推論モデルなので、答えが出る前に数百トークン考えます。スマホの GPU で毎秒 30 トークン出たとしても、短い質問への答えに 10 秒以上かかる計算です。

## 再現方法

```bash
# llama.cpp（/v1/systemone のある 2026-10 以降の版）
git clone --depth 1 https://github.com/ggml-org/llama.cpp && cd llama.cpp
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build --target llama-server -j
export LLAMA_SERVER=$PWD/build/bin/llama-server

# このリポジトリで
npm run download-liquid-models                 # GGUF 3 つ（約 5 GB）
npm run agent -- --decider d1-3b               # d1-3B を判断役に（d1-omni、lfm も可）
npm run agent -- --planner lfm-tools           # LFM2.5-2.6B が道具呼び出しで直接操作
npm run agent -- --planner lfm                 # LFM2.5-2.6B が手順を書き、EmbeddingGemma が判断
npm run download-phone-models -- lfm2.5-2.6b:q4:webgpu
npm run phone-check -- lfm2.5-2.6b:q4:webgpu --tokens 16
```
