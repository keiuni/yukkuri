# Gemma 4 の会話の例と、スマホ・アプリで動かすには（2026-10-09）

[前回の日本語の検証](japanese-chat-2026-10-08.md)の続きです。次の 3 つを調べました。

- **会話の例**: Gemma 4 E4B の会話の例を増やしました。新しく会話を 10 本（4〜5 往復、41 ターン）書き、「短く答えて」のシステムプロンプトを付けて答えさせました（[public/data/ja-talk.json](../public/data/ja-talk.json)）。
- **スマホ版の質**: 回答は、スマホのアプリが使うのと同じモデルファイル（LiteRT-LM 形式）で出しました。前回使った GGUF 版と、モデル名を伏せて比べました。
- **速さ・メモリ・アプリへの組み込み**: 公式の資料と、この環境での計測で確かめました。

環境はこれまでと同じクラウドコンテナ（CPU 4 コア、メモリ 16 GB、GPU なし）です。スマホの実機では測っていません。

## 結論

**スマホ版の Gemma 4 E4B は、雑談や相談の相手として十分使えます。ハイエンド機なら速さにも余裕があり、自分のアプリにも組み込めます。**
ただし、E4B は機種を選びます。もっと軽い E2B のスマホ版は、会話の質がはっきり落ちました。

1. **スマホ版の E4B は、新しい会話でも 7 割がそのまま使えた。**
   - 41 ターンのうち 71% がそのまま使え、95% は少し直せば使えました（採点役 2 人の平均）。
   - 関西弁を 4 往復保つ、謝るメッセージを書いてから短く直す、話が変わったあとも犬の名前と年を覚えている、ができました。
   - ときどき崩れます。韓国語の文字が混ざる（41 ターンで 1 回）、意味の通らない言い回し、ありえない助言（電気ポットでごはん）、頼まれた文を書かずに聞き返す、などです。
2. **スマホ版と GGUF 版の差は、E4B では小さく、E2B では大きい。**
   - E4B: そのまま使える回答はスマホ版 73%、GGUF 版 79% でした。
   - E2B: スマホ版 43%、GGUF 版 65% でした。新しい会話では 33% と 67% です。スマホ版の E2B は、提案を求められても聞き返すことが目立ちました。
   - 事実の問題（10 問 × 5 回）も、スマホ版は少し下がりました。E4B は 86%（GGUF 版 96%）、E2B は 58%（同 66%）です。
3. **速さは、ハイエンド機なら E4B でも余裕です。**
   - E4B は GPU で 22〜25 トークン/秒、最初の 1 トークンまで 1 秒弱です（公表値）。チャットの返信なら 2〜2.5 秒で出ます。
   - 重いのはメモリと容量です。E4B は作業メモリが約 3.4 GB、ファイルが 3.66 GB あり、RAM 8 GB 以上のハイエンド機向けです。
   - E2B は 1.5〜1.7 GB で、もっと多くの機種で動きます。ただし、上のとおり文面の質は一段下がります。
4. **アプリには入れられます。**
   - Google の LiteRT-LM（Apache 2.0）の Kotlin API（Android、安定版）か Swift API（iOS、早期プレビュー）で、同じファイルを読み込めば動きます。
   - この環境でも、スマホ版のファイルがそのまま CPU で動きました。メモリは約 3.4 GB で、モデルカードの値とほぼ同じです。

**どうするか**:
- ハイエンド機向けのアプリなら、E4B を入れて、システムプロンプトで「短く、チャットらしく」と指示します。
- 返信は下書きとして見せ、事実は検索と組み合わせます。
- 多くの機種で動かしたいなら E2B ですが、質が落ちます。用途を短い返信の下書きくらいに絞るのが安全です。

## 会話の例（スマホ版の Gemma 4 E4B）

スマホのアプリが使うのと同じファイル（`gemma-4-E4B-it.litertlm`）を LiteRT-LM で動かした回答です。手を加えずに、そのまま載せています。
システムプロンプトは前回の「短く」の指示と同じです。

> あなたはスマートフォンのチャットアプリのアシスタントです。友だちや同僚とのやり取りのように、自然な日本語で短く答えてください。見出しや箇条書きは、頼まれたときだけ使ってください。

- ユーザーの発言は前もって決めてあり、モデルの返事によって変えていません。そのため、会話が少しかみ合わないところがあります。
- サンプリングはモデルカードの推奨値で、乱数の種は 0 です（LiteRT-LM では種 1 と同じ答えになります）。
- 回答は平均 72 文字で、512 トークンの上限まで続いた回答はありませんでした。

  スマホ版の E2B は、答えずに質問で返すことが目立ちました。言葉の誤りもありました（下の表）。
- **事実**: スマホ版の E4B は、「日本一長い川」を 5 回中 2 回「阿賀野川」と答えました（正しくは信濃川）。スマホ版の E2B は、スカイツリーの高さを 504・358・534・354 m などと答え、634 m は一度も出ませんでした。
- **他の言語の混入**: 韓国語の文字が、E4B のスマホ版と GGUF 版で 1 回ずつ出ました（「포찌ちゃん」「맛있게 드세요」）。前回の 27 問でも、Gemma 4 には同じ混入がありました。
- **長さ**: 新しい会話の回答は平均 52〜78 文字で、512 トークンの上限まで続いた回答はありませんでした。

## スマホでの速さとメモリ

公式のモデルカード（[E4B](https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm)、[E2B](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm)）にある値です。
入力 1,024 トークン、出力 256 トークンで測ったもので、CPU は 4 スレッドです。

| モデル | 端末 | 動かす場所 | 出力の速さ | 最初の 1 トークンまで | メモリ |
| --- | --- | --- | ---: | ---: | ---: |
| E4B（ファイル 3.66 GB） | Galaxy S26 Ultra | GPU | 22.1 トークン/秒 | 0.8 秒 | CPU 側 710 MB（GPU 側は記載なし） |
| | Galaxy S26 Ultra | CPU | 17.7 トークン/秒 | 5.3 秒 | 3,283 MB |
| | iPhone 17 Pro | GPU | 25.1 トークン/秒 | 0.9 秒 | 3,380 MB |
| | iPhone 17 Pro | CPU | 9.7 トークン/秒 | 6.5 秒 | 961 MB |
| E2B（ファイル 2.58 GB） | Galaxy S26 Ultra | GPU | 52.1 トークン/秒 | 0.3 秒 | CPU 側 676 MB |
| | Galaxy S26 Ultra | CPU | 46.9 トークン/秒 | 1.8 秒 | 1,733 MB |
| | iPhone 17 Pro | GPU | 56.5 トークン/秒 | 0.3 秒 | 1,450 MB |
| | iPhone 17 Pro | CPU | 25.0 トークン/秒 | 1.9 秒 | 607 MB |

- **速さ**: Gemma 4 の日本語は、1 トークンが約 1.8 文字でした（前回の回答で計算）。チャットの返信（60 文字前後）は 30〜35 トークンです。
  そのため E4B を GPU で動かせば、返信は 2〜2.5 秒で出ます（最初の 1 トークンまでの時間を含む）。E2B なら 1 秒前後です。
- **投機的デコード**: 下書き用の小さなモデルを併用する仕組みです。モデルカードでは、Galaxy S26 Ultra の GPU で E4B が 37〜49 トークン/秒、E2B が 67〜92 トークン/秒まで上がります。
- **公表値はハイエンド機だけです。** 中位機や数年前の機種の値は見つかりませんでした。それらの機種では、これより遅くなります。
- **メモリ**: E4B は作業メモリが約 3.3〜3.4 GB 要ります（Android の CPU、iPhone の GPU）。RAM 8 GB の機種では、ほかのアプリと取り合いになるおそれがあります。12 GB 以上なら余裕があります。
  E2B は 1.5〜1.7 GB なので、RAM 6〜8 GB の機種でも収まります。公式の「必要な RAM」は出ていないため、この段落は使用量からの目安です。

### この環境で測った値（スマホ版のファイル、CPU 4 スレッド）

スマホと同じファイルを、この環境の CPU（x86、4 スレッド）で `litert-lm benchmark` にかけた値です（入力 1,024 トークン、出力 256 トークン）。
スマホの CPU とは別物なので、速さは参考です。メモリはモデルカードの CPU の値（3,139〜3,283 MB）とほぼ同じでした。

| 条件 | 入力の読み込み | 出力の速さ | 最初の 1 トークンまで | メモリ（最大） |
| --- | ---: | ---: | ---: | ---: |
| E4B（重みのキャッシュあり。既定） | 146〜151 トークン/秒 | 9.6 トークン/秒 | 6.9〜7.1 秒 | 3.4 GB |
| E4B（投機的デコードを強制） | 148 トークン/秒 | 5.7 トークン/秒 | — | 3.5 GB |
| E4B（キャッシュなし） | 77 トークン/秒 | 7.6 トークン/秒 | 13.5 秒 | 13.6 GB（もう 1 回は強制終了） |
| E2B（重みのキャッシュあり） | 323 トークン/秒 | 18.2 トークン/秒 | 3.2 秒 | 1.8 GB |
| 参考: E4B の GGUF 版（llama.cpp、Q4_0） | — | 5.6 トークン/秒 | — | — |

- **キャッシュ**: 初回の読み込みで、CPU 向けに並べ替えた重みがモデルの横に保存されます（E4B で約 2.5 GB）。2 回目からはそれを使うので、読み込みは 1 秒ほどで終わります。
- **投機的デコード**: この CPU では、かえって遅くなりました（9.6 → 5.7 トークン/秒）。既定の設定（auto）では使われていませんでした。
- **会話での時間**: 新しい会話 41 ターンは、1 ターンあたり中央値で E4B が 5.9 秒、E2B が 2.6 秒でした（回答は平均 72 文字と 52 文字）。
  ただし、LiteRT-LM のサーバーは毎回会話を最初から読み直します。アプリでは会話を持ち続けるので、読み直しの時間はかかりません。

## アプリに入れるには

**入れられます。** Gemma 4 も、動かすためのライブラリ LiteRT-LM も Apache 2.0 で、商用のアプリにも組み込めます。
Google の「AI Edge Gallery」アプリも、このライブラリで動いています。

| 方法 | 対応 | 状態 | メモ |
| --- | --- | --- | --- |
| LiteRT-LM（Kotlin） | Android | 安定版 | モデルファイル（.litertlm）をアプリで読み込む。GPU・NPU も使える |
| LiteRT-LM（Swift） | iOS / macOS | 早期プレビュー | Metal（GPU）対応。API が変わる可能性あり |
| flutter_gemma | Android / iOS | コミュニティ製 | Flutter から LiteRT-LM を使う |
| Android の AICore（Gemini Nano） | 一部の Android 機 | ML Kit Prompt API はベータ | モデルを配る必要がない。モデルカードは「Gemma 4 は AICore で Gemini Nano として使え、製品にはこちらを推奨」としている。ただし最新の機種だけ（nano-v4 は Pixel 11 シリーズ、Galaxy Z Flip8 / Fold8 など） |
| Apple の Foundation Models | Apple Intelligence 対応の iPhone | 提供中 | Gemma ではなく Apple のモデル。日本語に対応。モデルを配る必要がない |

### Android（Kotlin）の最小の例

[LiteRT-LM の Kotlin ガイド](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/kotlin/getting_started.md)の書き方に、今回の設定を入れたものです。

```kotlin
// build.gradle.kts
dependencies {
    implementation("com.google.ai.edge.litertlm:litertlm-android:latest.release")
}
```

```kotlin
// モデルは初回起動時にダウンロードしておく（例: filesDir/gemma-4-E4B-it.litertlm）
val engine = Engine(
    EngineConfig(
        modelPath = File(context.filesDir, "gemma-4-E4B-it.litertlm").path,
        backend = Backend.GPU(),           // GPU がない機種は Backend.CPU()
        cacheDir = context.cacheDir.path,  // 2 回目からの読み込みが速くなる
    )
)
engine.initialize() // 数秒〜10 秒かかるので、UI スレッドの外で呼ぶ

val conversation = engine.createConversation(
    ConversationConfig(
        systemInstruction = Contents.of(
            "あなたはスマートフォンのチャットアプリのアシスタントです。友だちや同僚とのやり取りのように、" +
            "自然な日本語で短く答えてください。見出しや箇条書きは、頼まれたときだけ使ってください。"
        ),
        samplerConfig = SamplerConfig(topK = 64, topP = 0.95, temperature = 1.0),
    )
)
conversation.sendMessageAsync("今日の晩ごはん、何にしよう。") // コルーチンの中で
    .collect { print(it.toString()) }                          // 少しずつ表示する
```

- GPU を使うには、`AndroidManifest.xml` の `<application>` に `libvndksupport.so` と `libOpenCL.so` の `<uses-native-library>` を書きます（ガイドのとおり）。
- 会話の履歴は `conversation` が持ちます。前回までの話を覚えたまま続けられます。

### 作るときの注意

- **モデルの配り方**: ファイルが 2.6〜3.7 GB あるので、アプリ本体には入れず、初回起動時にダウンロードするのが普通です（Gallery アプリも Hugging Face から取得します）。Wi-Fi でのダウンロードと、ストレージの空きの確認を入れておくと安全です。
- **ストレージ**: E4B はファイルだけで 3.66 GB です。この環境では、CPU で動かしたときに重みを並べ替えたキャッシュ（約 2.5 GB）もモデルの横に作られました。
- **キャッシュ**: この環境では、キャッシュを切ると E4B が最大 13.6 GB のメモリを使い、もう 1 回は強制終了しました（キャッシュありは 3.4 GB）。CPU で動かすなら、`cacheDir` を指定しておくべきです。
- **読み込み時間**: ガイドによると、`engine.initialize()` に最大 10 秒ほどかかります。アプリの起動直後に裏で読み込んでおくと、待たせずに済みます。
- **機種の幅**: たくさんの機種で動かしたいなら、E2B（メモリ 1.5〜1.7 GB）が無難です。E4B はハイエンド機向けです。
- **参考になる実装**: [Google AI Edge Gallery](https://github.com/google-ai-edge/gallery)（Apache 2.0、Android 12 以上・iOS 17 以上）のソースコードです。

## 再現方法

```bash
cd embeddinggemma-demo
pip install litert-lm                     # LiteRT-LM のコマンド（uv tool install litert-lm でもよい）
npm run download-chat-models -- gemma4-e4b-litert gemma4-e2b-litert gemma4-e4b gemma4-e2b
export LITERT_LM=$(command -v litert-lm) LLAMA_SERVER=/path/to/llama.cpp/build/bin/llama-server
npm run ja-chat -- --short --data ja-talk gemma4-e4b-litert gemma4-e4b gemma4-e2b-litert gemma4-e2b   # 新しい会話 10 本
npm run ja-chat -- --short gemma4-e4b-litert gemma4-e2b-litert   # 前回の 27 問（GGUF 版は前回の結果を使う）
node scripts/ja-facts.mjs gemma4-e4b-litert gemma4-e2b-litert    # 事実 10 問 × 5 回
R=gemma4-e4b-short,gemma4-e4b-litert-short,gemma4-e2b-short,gemma4-e2b-litert-short
node scripts/ja-chat-judge.mjs pack 4 --tag phone --runs $R      # 採点用の資料（pass 5 も同じ）
node scripts/ja-chat-judge.mjs score --tag phone --runs $R       # 採点の集計
litert-lm benchmark models/litert-community/gemma-4-E4B-it-litert-lm/gemma-4-E4B-it.litertlm \
  --backend cpu --cpu-thread-count 4 -p 1024 -d 256
```

- スマホ版は、LiteRT-LM の OpenAI 互換サーバー（`litert-lm serve`）で動かしています（[scripts/lib/litert-server.mjs](../scripts/lib/litert-server.mjs)）。GGUF 版と同じリクエストを送れます。
- 採点役には、資料のファイルだけを読み、結果を JSON で書くように指示しました（ほかのファイルを開くとモデル名がわかるため）。

## 注意点

- **回答の数**: 各問題の回答は、1 モデル 1 回だけです。乱数の種を変えると、答えは変わります。
- **乱数の種**: LiteRT-LM では、種 0 が種 1 とまったく同じ答えになりました。そのため、事実の問題ではスマホ版だけ種 1〜5 を使いました。
- **採点**: 採点したのは Claude で、人ではありません。モデル名を伏せ、並び順を変えて 2 回採点させました。
- **同じ種でも同じ文にはならない**: スマホ版と GGUF 版は、動かすライブラリも重みの圧縮も違います。比べられるのは、全体の傾向だけです。
- **会話の作り方**: ユーザーの発言は前もって決めてあり、モデルの返事に合わせて変えていません。
- **速さとメモリ**: この環境の値は x86 の CPU のものです。スマホの値はモデルカードの公表値で、実機では確かめていません。発熱や電池の減りも調べていません。
